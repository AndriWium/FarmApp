# Decisions

One line per irreversible-ish decision, dated.

- 2026-09-15: Swagger bearer-auth padlock (doc 13 Phase 0a) is wired via Swashbuckle's own `AddSwaggerGen`/`UseSwagger` document generation instead of the previously-used `Microsoft.AspNetCore.OpenApi` `AddOpenApi`/`MapOpenApi`. Reason: .NET 10 ships `Microsoft.OpenApi` 2.x, which removed the concrete `OpenApiSecurityScheme`/`OpenApiReference` types `AddOpenApi`'s document-transformer API expected; Swashbuckle.AspNetCore 10.2.3 already targets the new model with a stable, documented `AddSecurityDefinition`/`AddSecurityRequirement` API (the latter now takes an `OpenApiSecuritySchemeReference` via a `Func<OpenApiDocument, OpenApiSecurityRequirement>` delegate). Swagger UI now serves from `/swagger/v1/swagger.json` instead of `/openapi/v1.json`. No spec doc was wrong — doc 13 just said "standard ASP.NET Core JWT+Swashbuckle setup," which this now literally is.
- 2026-09-15 (Phase 0b-1): `InputItem.Category` is the first enum in the codebase. Stored `.HasConversion<string>().HasMaxLength(20)` per doc 11. Also registered `JsonStringEnumConverter` globally in `Program.cs` (`AddJsonOptions`) so the API/Swagger layer serializes enums as readable strings too, not just the DB column — otherwise System.Text.Json's default numeric enum serialization would contradict the "strings for report readability" intent one layer up. Future enums inherit this for free.
- 2026-09-15 (Phase 0b-1): field caps not spelled out in doc 02/the task brief, chosen consistent with existing precedent (Grade/Block `Name` = 50, `Block.Note` = 500): `InputItem.Unit` = `HasMaxLength(20)` (e.g. "kg", "L", "bag", "each"); `PriceList.Name` = `HasMaxLength(50)`; `Supplier.Name`/`Supplier.Phone` = `HasMaxLength(50)`, `Supplier.Phone` optional.
- 2026-09-15 (Phase 0b-2): `PackSize` has no `IsActive` column - per the doc brief's own suggestion, a pack size is small enough that a mistake is just deleted and recreated, so `PackSizeService.DeleteAsync` performs a real `DELETE`, the first hard-delete in the codebase (everything else is soft-delete). Scoped uniqueness `(ProductId, Name)` still enforced via a unique index.
- 2026-09-15 (Phase 0b-2): `Product.CropId`/`Product.MakeMode` are nullable and not hard-restricted to their "natural" `ProductType` (e.g. nothing stops a `CropId` on a `Resale` product) - the doc brief explicitly calls this out as real-world nuance a human should be able to override, so only the referential-integrity check (CropId must reference a real Crop, when provided) is enforced.
- 2026-09-15 (Phase 0b-2): `Price.PackSizeId` made nullable (per brief) to support "price per base unit, no specific pack" (loose kg pricing). A filtered unique index `IX_Prices_ActiveCombo` on `(PriceListId, ProductId, GradeId, PackSizeId) WHERE ValidTo IS NULL` enforces at the DB level that at most one price row is "current" per combination, as a backstop to `SetPriceAsync`'s own read-then-close-then-insert logic.
- 2026-09-15 (Phase 0b-2): `Price` write path exposes only `SetPriceAsync` (upsert-with-history) via `POST /api/v1/prices` - deliberately no `PUT`/`DELETE`, since prices are never updated or deleted, only superseded. Reads are `GET /api/v1/prices/current` and `GET /api/v1/prices/history`, both taking `priceListId`/`productId`/`gradeId`/`packSizeId` as query params (not personal data, so query params are fine per doc 11). `ValidFrom`/`ValidTo` use `DateOnly` (mapped to SQL `date`) - the EF Core/SQL Server provider handled it cleanly, no friction.
- 2026-09-15 (Phase 0b-2): `RecipeLine` is modeled as a sub-resource of `Product` (`IProductService.SetRecipeAsync`/`GetWithRecipeAsync`, `PUT`/`GET /api/v1/products/{id}/recipe`), not a standalone CRUD - matches the doc brief. It has its own `IRecipeLineRepository` in Domain (repository pattern still applies internally) but no controller of its own. Also added a unique index on `(ProductId, InputItemId)` (not spelled out in the brief) - the same ingredient listed twice in one recipe would silently double-count cost/depletion with no legitimate use case, so it's blocked at the DB level.
- 2026-09-15 (Phase 1a): `StockMovement` implements `IPeriodLocked` (`BusinessDate => Date`, explicit interface implementation). `PeriodLockInterceptor` was scaffolded in Phase 0a explicitly anticipating "Sale and StockMovement (Phase 1/2) will be the first" - wiring it in now means no later migration/retrofit is needed and matches the codebase's own stated intent. Cost: none (BusinessDate is computed, not a persisted column) - a movement dated into a closed accounting month is now rejected at save time.
- 2026-09-15 (Phase 1a): the movement-recording service (`IStockMovementService`) covers only outflow/depletion movement types (Wastage, OwnUse, Sample, Donation, Adjustment, Repack, TransferOut+TransferIn) - all FIFO-allocated across existing batches via `IStockAllocationService`. `Adjustment` here is specifically a *downward* adjustment (stock-take shortfall/shrinkage): a *positive* "found extra stock" adjustment isn't supported by this endpoint, since FIFO-allocating a positive quantity across existing batches doesn't make sense (a positive adjustment would need to create a new `StockBatch`, which is a different operation, out of scope until Phase 1's own StockTake feature is built). `Repack` is likewise modeled as a plain negative depletion (stock leaving its current tracked form/pack size) - the brief's request shape for Repack (ProductId/GradeId/Qty/Reason/LocationId, identical to Wastage) doesn't carry a "target product/pack size," so no offsetting "repack-in" movement is created this phase.
- 2026-09-15 (Phase 1a): added `POST/GET /api/v1/stock-batches` (`StockBatchesController`/`StockBatchService`) as a direct-creation endpoint for `StockBatch`, restricted to `Source: Harvest|Purchase` (rejects `Production` - `ProductionBatch` needs `StockMovement` to exist first, which the task brief itself calls circular). This is a documented stopgap: Phase 1b's real purchase-in/harvest-in use cases will create batches through their own flows. Creating a batch also seeds one initial `HarvestIn`/`PurchaseIn` movement for `QtyIn` in the same request, since on-hand is always derived from the movement ledger (doc 02) - a batch with no movement would show zero on hand despite a non-zero `QtyIn`. Because `StockMovement.StockBatchId` has no navigation property (matches the rest of the codebase's loose-FK convention), the batch is saved first to materialize its id, then the seeding movement is added and saved again - two `SaveChangesAsync` calls, not the "one atomic call" the brief specifies for the *movement-recording* service (which never creates new batches, so never hits this problem).
- 2026-09-15 (Phase 1a): `StockMovementsController`'s six depletion endpoints (wastage/own-use/sample/donation/adjustment/repack) and `/transfer` all require `CanManageMasterData` (no `CanManageStock` policy exists yet, per the task brief's own instruction not to invent new auth policies this phase). A dedicated `CanManageStock` policy would be more precise long-term and is worth adding once Phase 2's till/POS roles clarify who should be allowed to record stock movements day-to-day.
- 2026-09-15 (Phase 1a): `IStockMovementRepository.GetOnHandSummaryAsync`'s Product/Grade grouping is done **client-side** (materializes the flat movement/batch/product/grade join via `ToListAsync`, then `GroupBy`/`Sum` in memory) rather than server-side. EF Core 10 cannot translate a `GroupBy` + `Sum` whose key/aggregate expressions reach back through multiple joins' transparent identifiers directly into a record constructor (`InvalidOperationException: ... could not be translated`); splitting it into a "flat projection, then GroupBy" over the *same* `IQueryable` doesn't help either, since nothing forces evaluation in between - it's still one expression tree at translation time. Materializing first is the simplest fix and is fine at this phase's data volumes (a small farm's whole movement ledger); if this becomes a real report over a large ledger, doc 04's `Reporting.StockOnHand` view (raw SQL/Dapper, bypassing repositories entirely) is the intended long-term answer per doc 11.
- 2026-09-15 (Phase 1b): `ProducePurchaseLine` carries exactly doc 02's field list (`ProducePurchaseLineId, ProducePurchaseId, ProductId, GradeId, Qty, UnitCost`) - no `ShelfLifeDays` column, since it's not in that list. But building the line's `StockBatch` (via `IStockBatchService.CreateAsync`, reused rather than duplicated) requires a `ShelfLifeDays > 0`, and nothing upstream (`Product`, `Grade`) carries a default shelf life to fall back on. `CreatePurchaseLineRequest` (the API request DTO, not the persisted entity) therefore carries `ShelfLifeDays` as a required per-line input that flows straight into the batch it creates and is never persisted on `ProducePurchaseLine` itself. `IProducePurchaseService.CreatePurchaseAsync` validates the supplier and every line's product/grade *before* writing anything (header insert, line inserts, and per-line batch+movement creation are three separate save points - the two-phase-save stopgap `StockBatchService.CreateAsync` already established, extended to three phases here since `ProducePurchaseLineId` must exist before it can become `StockBatch.PurchaseLineId`), so a bad reference is rejected up front rather than leaving a partially-built purchase.
- 2026-09-15 (Phase 1b): `StockMovementService` gained `RecordBatchAdjustmentAsync(stockBatchId, signedQty, reason, locationId, ct)` - a single signed `Adjustment` movement against one already-known batch, no FIFO allocation (the caller, `StockTakeService`, already knows exactly which batch a stock-take line counts, so there's no product/grade to allocate across). This is additive: the existing `RecordAsync(StockMovementType.Adjustment, ...)` path behind `POST /api/v1/stock-movements/adjustment` is untouched and stays downward-only/FIFO-allocated across a product/grade, per the task brief's instruction to leave the six existing depletion endpoints as they are. `RecordBatchAdjustmentAsync` deliberately does **not** call `SaveChangesAsync` - it adds the movement to the tracked `IStockMovementRepository` and lets the caller control the transaction boundary, since `StockTakeService.RecordCountsAsync` needs one atomic save covering every line's `CountedQty`/`Variance` update *and* every resulting adjustment movement across a whole stock take, not one save per line.
- 2026-09-15 (Phase 1b): `StockTake`/`StockTakeLine` never create a `StockBatch` - doc 02's `ProductId/BatchId` notation for the line means each line counts a specific existing `StockBatchId` (received earlier via harvest-in or purchase-in), so both directions of variance become a single signed `Adjustment` against that same batch. `StartStockTakeAsync` validates every given `StockBatchId` (and `LocationId`, if given) exists before writing anything, then snapshots each line's `SystemQty` from `IStockMovementRepository.GetOnHandAsync` at start time - never trusted from the client. `RecordCountsAsync` re-validates every `StockTakeLineId` belongs to the given stock take before mutating any of them, then sets `CountedQty`/`Variance` and - for non-zero variances - calls the new `RecordBatchAdjustmentAsync` per line, committing every line update and every movement in one `SaveChangesAsync`.
- 2026-09-15 (Phase 1b): `StockTakeService.RecordCountsAsync` is re-callable against the same stock-take lines - nothing rejects a second `POST .../counts` call naming an already-counted line. Each call computes `Variance` against the line's original `SystemQty` snapshot (never against a running total), so re-recording with a corrected count produces a second, independent adjustment movement rather than a delta. Acceptable for this phase - none of Phase 1's endpoints have `ClientGuid`/idempotency wired up yet (that's doc 08, deferred to Phase 2's `Sale`) - but worth tightening later (reject a second count on an already-counted line, or require an explicit re-open) once a real counting workflow shows whether recounts are a normal correction path or a mistake worth guarding against.
- 2026-09-15 (Phase 2a): `IUnitOfWork` gained `BeginTransactionAsync`/`CommitTransactionAsync`/`RollbackTransactionAsync`, implemented by `FarmAppDbContext` wrapping `Database.BeginTransactionAsync()` (an `IDbContextTransaction` kept in a private field - not exposed through the interface, so Domain/Application code depending on `IUnitOfWork` never needs an EF Core reference). This is a genuinely new, better pattern for this codebase, used for the first time by `SaleService.CreateSaleAsync`: everything from the `Sale` header insert through every line's stock depletion, every `SaleLine`, and every `SalePayment` now lives inside one real database transaction, so a mid-operation failure (most notably `InsufficientStock` on a later line) rolls back *everything*, including the header's own already-flushed `SaveChangesAsync` - not just whatever was still sitting unflushed in the change tracker. This is a materially stronger guarantee than `ProducePurchaseService`/`StockBatchService`/`StockTakeService`'s older two-phase-save stopgap (sequential `SaveChangesAsync` calls with only pre-validation narrowing the failure window - see the Phase 1a/1b entries above) - those three would benefit from the same treatment, but retrofitting them is out of this phase's scope; worth doing once a POS-scale write volume makes their existing failure window worth closing too.
- 2026-09-15 (Phase 2a): `TillSessionService.OpenAsync`/`SaleService.CreateSaleAsync` take the acting user's id (`openedByUserId`)/derive nothing user-related respectively as a plain method parameter rather than injecting `IHttpContextAccessor` into the `Application` layer. `TillSessionsController.Open` reads `ClaimTypes.NameIdentifier` off the authenticated `ClaimsPrincipal` itself and passes it in - keeping the JWT-claims dependency in Presentation, where doc 11 says HTTP-specific concerns belong, rather than reaching for `IHttpContextAccessor` the way `AuditInterceptor` (Infrastructure, a different layer with different rules) already does. Functionally identical to the brief's suggestion, just drawn on the Presentation/Application side of the line instead.
- 2026-09-15 (Phase 2a): `StockMovementService` gained `RecordSaleDepletionAsync(productId, gradeId, qtyBaseUnits, saleId, locationId, ct)` - the `SaleOut` counterpart to `RecordBatchAdjustmentAsync` rather than an extension of `RecordAsync`'s six-type switch (same "don't generalize the existing six, add a new method shaped like them" instruction as Phase 1a). It fetches each FIFO-allocated batch's `UnitCost` (`IStockBatchRepository.GetUnitCostsByIdsAsync`, new) and returns both the raw per-batch allocations (`SaleDepletionResult.Allocations`) and the resulting movement DTOs - it deliberately does **not** compute the weighted-average cost itself (that's `SaleService`'s job, via the Domain's `ISaleLineCalculator.WeightedAverageCost`), keeping "what batches did this touch, at what cost" (a stock-movement concern) separate from "what does a sale line's cost snapshot become" (a sale concern). Like `RecordBatchAdjustmentAsync`, it does not call `SaveChangesAsync` itself - `SaleService` owns the transaction boundary for the whole sale. Movements are tagged `RefTable: "Sale"`/`RefId: saleId` - the first real use of `StockMovement.RefTable`/`RefId`, which every prior movement-writing path has left null.
- 2026-09-15 (Phase 2a): the pack-size-to-base-unit conversion and the sale-line weighted-average-cost calculation both live in `FarmApp.Domain.Services.SaleLineCalculator` (interface `ISaleLineCalculator`) rather than inline in `SaleService` - same "costing is Domain, not Api" precedent as `IStockAllocationService`, and per the task brief's own instruction to put arithmetic this easy to get subtly wrong somewhere unit-testable. Both are covered in `tests/FarmApp.Domain.Tests/Services/SaleLineCalculatorTests.cs`, including the "spans batches at different costs" case that a naive first-batch-only or plain-average implementation would get wrong.
- 2026-09-15 (Phase 2a): four new `ServiceError` cases (`TillSessionAlreadyOpen`, `TillSessionClosed`, `PaymentMismatch`, `AccountPaymentRequiresCustomer`) were added rather than reusing `NotFound`/`DuplicateName` - each is a distinct business rule with its own 409 message in `ApiControllerBase`, and none of the existing cases fit without being misleading. Every other new failure mode in `SaleService.CreateSaleAsync` (missing till session/customer/product/grade/pack-size, or a pack size that exists but belongs to a different product) reuses plain `NotFound`, matching `ProducePurchaseService`'s precedent of a single generic entity-name string in the controller rather than a per-field detail message.
- 2026-09-15 (Phase 2a): `TillSession`/`Sale`'s day-close and refund/balance features are explicitly out of scope this phase (task brief): `TillSession.SystemCardTotal`/`CardMachineBatchTotal`/`Difference`/`DifferenceNote` are present as nullable columns (doc 02's field list) but nothing writes them yet - there is no `CloseAsync`. `Sale.Status` is always written as `Complete`; nothing transitions a sale to `Refunded` yet. A customer's outstanding balance is never stored anywhere (`SalePayment` rows with `Method: Account` are the only record) and no read endpoint for it exists yet - it needs `CustomerPayment` (Phase 2b) to be subtracted from first.
- 2026-09-15 (Phase 2a, found during live verification): `SaleService.CreateSaleAsync`'s per-line loop now calls `uow.SaveChangesAsync(ct)` immediately after each line's `RecordSaleDepletionAsync` call succeeds, not just once at the end. Without this, a multi-line sale depleting the *same* product/grade twice (e.g. a loose-kg line and a packed line of the same product, spanning batches) got the wrong `CostAtSale` on the second line and could silently over-allocate a batch beyond its physical on-hand: `IStockMovementRepository.GetAvailableBatchesAsync` re-reads on-hand from the database via `AsNoTracking`, not from the DbContext's change tracker, so a second line's FIFO query didn't see the first line's just-added (but still unflushed) `StockMovement` rows and computed availability from a stale snapshot. Caught in this phase's own required verification (check #2: a 12kg line fully draining a 5kg batch, followed by a 1.5kg packed line that should have spilled into the next, more expensive batch - it instead "found" 5kg still sitting in the first batch and priced itself at that batch's cost instead of the correct one). The extra flush stays inside the one transaction `BeginTransactionAsync` already opened, so atomicity is unaffected - a later line's failure still rolls every earlier flush back too (re-verified via direct SQL: a deliberately over-depleting request left zero `Sales`/`SaleLines`/`SalePayments`/`StockMovements` rows behind).
- 2026-09-15 (Phase 2a, found during live verification): `CreateSaleAsync` originally always returned via `CreatedAtAction` (201), even on an idempotent replay - doc 08 explicitly says a replayed `ClientGuid` should return 200 ("do nothing, return the existing sale"), not 201. Fixed by introducing `CreateSaleResult(SaleDto Sale, bool WasReplay)` as `ISaleService.CreateSaleAsync`'s return payload; `SalesController.Create` now answers `Ok(sale)` when `WasReplay` is true and `CreatedAtAction(...)` (201) otherwise, so a retrying offline client can distinguish "this already existed" from "I just created this" the way doc 08 describes.
- 2026-09-15 (Phase 2b): `TillSessionService.CloseAsync` computes `SystemCardTotal` via a new `ISalePaymentRepository.GetCardTotalForTillSessionAsync` - a `SalePayment` join `Sale` query (`WHERE Sale.TillSessionId = @id AND Sale.Status = Complete AND SalePayment.Method = Card`), not a method on `ITillSessionRepository`/`ISaleRepository`. The query's primary aggregate is over `SalePayment` rows, so it lives on that repository (same "repository owns the query whose primary entity it aggregates" reasoning as `IStockMovementRepository.GetOnHandSummaryAsync`), joining `Sale` only to filter. `Status == Complete` is the load-bearing filter that makes day-close correct without any special-casing: a sale refunded within the same session before close is silently excluded, no extra logic needed in `CloseAsync` itself. `GetAccountTotalForCustomerAsync` (added alongside, for `CustomerPaymentService.GetBalanceAsync`, Phase 2b's other half) follows the identical shape - both use the `SumAsync(x => (decimal?)x, ct) ?? 0m` pattern already established by `IStockMovementRepository.GetOnHandAsync`, since `SumAsync` over an empty non-nullable `decimal` sequence throws.
- 2026-09-15 (Phase 2b): `CloseAsync` is a single-entity write (one `SaveChangesAsync`, no `BeginTransactionAsync`) - same "single-entity write, one atomic save" precedent as `OpenAsync`. There's a read (`GetCardTotalForTillSessionAsync`) before the write, but nothing else is mutated in between, so there's no multi-step operation to protect with a real transaction the way `SaleService.CreateSaleAsync`/`RefundSaleAsync` need one.
- 2026-09-15 (Phase 2b): `TillSessionDto` gained the four day-close fields (`SystemCardTotal`, `CardMachineBatchTotal`, `Difference`, `DifferenceNote`) so `POST .../close`'s response (and any later `GET`) can show the computed reconciliation, not just `ClosedAt`. `OpenAsync`'s response naturally carries them as null (nothing writes them until close).
- 2026-09-15 (Phase 2b): `CustomerPayment.Method` is a **new enum** (`CustomerPaymentMethod: Cash|Card|EFT`), not a reuse of `SalePaymentMethod`. `SalePaymentMethod.Account` means "put this sale on the tab" - it describes how a *sale* was paid for, and is meaningless as an answer to "how did the customer pay off their account" (you can't settle a debt by putting it on the same debt). The other two `SalePaymentMethod` values (`Card`/`EFT`) would have fit, but reusing the enum would still expose the nonsensical `Account` value on every `CustomerPayment` write with nothing stopping a client from picking it. A plain `string` was also considered (simplest, "don't over-engineer") but rejected: `Method` genuinely has a small closed set of real values and doc 11's own rule is enums-stored-as-strings for exactly this shape of field. `CustomerPaymentMethod` also adds `Cash` - the POS's card-only decision (doc 01 §4) is specifically about removing float/change/cash-security complexity *at the till*; settling a debt away from the till (a customer arriving with cash, or paying via EFT from home) carries none of those complications, so there's no reason to forbid cash there the way the till does.
- 2026-09-15 (Phase 2b): `CustomerPaymentService.GetBalanceAsync` returns `null` (not a `ServiceResult`/`ServiceError`) when the customer doesn't exist, matching the existing `GetByIdAsync`-returns-nullable convention (`CustomersController.GetById`) rather than introducing a `ServiceResult<CustomerBalanceDto>` for a single not-found case. `CustomersController` calls it directly (`GET /api/v1/customers/{id}/balance`), so the controller now takes both `ICustomerService` and `ICustomerPaymentService` as constructor dependencies - still just "translate HTTP to service call(s)" (doc 11), not business logic living in the controller.
- 2026-09-15 (Phase 2b): balance's "owed" side (`ISalePaymentRepository.GetAccountTotalForCustomerAsync`) and day-close's `GetCardTotalForTillSessionAsync` (see above) both filter `Sale.Status == Complete`, which is *why* refunds (Sale.Status transitions to `Refunded`) matter for balance/day-close correctness without either query needing special-casing for "was this later refunded" - a refunded sale's Account or Card portion simply falls out of both sums the moment `RefundSaleAsync` flips the status.
- 2026-09-15 (Phase 2b): `RefundSaleAsync`'s stock reversal reuses the existing `Adjustment` movement type (`RefTable: "Sale"`/`RefId: saleId`, positive Qty crediting the same `StockBatchId` the original `SaleOut` depleted) rather than adding a new `StockMovementType` enum value (e.g. `SaleReturn`). Reasoning: `StockTake` already uses `Adjustment` for its own bidirectional corrections (positive "found more than expected", negative "found less"), so a refund crediting stock back is the same *kind* of event from the ledger's point of view - a correction against a specific batch, not a new depletion/receipt. The alternative (a dedicated `SaleReturn` type) would read slightly better in a future movement-type breakdown report, but `RefTable`/`RefId` already gives full traceability back to the originating sale without it, and doc 11's own precedent (`StockTake`) is to reuse `Adjustment` for exactly this "known correction against a known batch" shape rather than growing the enum per new correction source. Revisit if reporting ever needs to distinguish "stock-take variance" from "sale refund" adjustments at the aggregate level.
- 2026-09-15 (Phase 2b): the reversal is implemented as `IStockMovementService.ReverseSaleDepletionAsync(saleId, reason, ct)` - the inverse counterpart to `RecordSaleDepletionAsync`, not a new method on `IStockMovementRepository` called directly from `SaleService`. It fetches the sale's original `SaleOut` movements via a new `IStockMovementRepository.GetBySaleDepletionAsync(saleId, ct)` (returns `SaleDepletionMovement(StockBatchId, Qty, LocationId)` records, matching `GetAvailableBatchesAsync`'s "repository returns a plain record list, never a leaked `IQueryable`" convention) and writes one offsetting `Adjustment` movement per original movement, at the *same* `StockBatchId` and magnitude - deliberately never re-running `IStockAllocationService.AllocateFifo`, since a refund is undoing a specific already-known past action, not making a new allocation choice (FIFO could easily pick a *different* batch than the one originally sold from, which would be wrong). Like `RecordSaleDepletionAsync`/`RecordBatchAdjustmentAsync`, it does not call `SaveChangesAsync` itself - `SaleService.RefundSaleAsync` owns the transaction boundary (`BeginTransactionAsync`/.../`CommitTransactionAsync`, the same genuine-EF-Core-transaction pattern `CreateSaleAsync` established in Phase 2a, per the task brief's explicit instruction not to fall back to the older two-phase-save stopgap).
- 2026-09-15 (Phase 2b): `RefundSaleAsync`'s optional `reason` has no dedicated column (doc 02's `Sale` field list has none) - it's folded into `Sale.Notes` (`"Refund: {reason}"`, appended with `" | "` if `Notes` already had content) rather than silently discarded, and also flows into each reversal `StockMovement.Reason` (`"Refund of Sale {id}: {reason}"`) so it's visible from either side of the reversal without a schema change. A dedicated `RefundReason` column would be cleaner long-term if refunds become frequent enough to want to query/report on reasons separately.
- 2026-09-15 (Phase 2b): `RefundSaleAsync` does not validate that the sale's `TillSession` is still open, or that it's being refunded within the same session it was sold in - the task brief's live-verification checklist explicitly exercises refunding a sale *after* its original till session has been closed (and checks a *new* session's day-close correctly excludes it), so refunding across closed/new sessions is expected, normal behaviour, not an edge case to guard against.
